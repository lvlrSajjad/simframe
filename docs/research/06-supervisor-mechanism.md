# Research answer — the supervisor/executor mechanism (simframe), 2026-09-11

## TL;DR
- **The token-masking safety property is real and confirmed by Apple's own words**: `@Generable` enum constraints are enforced at the sampling layer via logit masking, so a fourth word is physically unrepresentable — your safety argument holds at the layer you hoped. But the "wait" mechanism is largely re-derivable without a model (your transition graph already stores p95 edge timings), and your A/B is confounded exactly as you suspect: the static briefing, not the runtime critic, is doing most of the work, which matches the published agent-memory literature (AutoGuide, Agent Workflow Memory, Contextual Experience Replay).
- **Your Q1 context-window failure was the documented failure mode**: 4,096 tokens is the fixed, now-queryable ceiling (`SystemLanguageModel.contextSize`, iOS/macOS 26.4), it counts input+output combined, there is no transcript-pruning API (fresh session per judgement is the intended pattern), `prewarm()` is the supported warm, and a session handles exactly one in-flight request (`isResponding`; concurrent calls throw `rateLimited`).
- **On ordering: promote item 97 (selective prediction / conformal abstention) ahead of item 96 (the 2×2 experiment)** — an explicit abstain token is the one vocabulary addition that buys coverage without widening what the component can *do*, and it is the cheapest fix to your two mis-rulings, both of which were missing-vocabulary cases, not reasoning failures. Run the "briefing, no model" arm as part of 96, but the highest-reliability lever is abstention, applied first.

## Key Findings

1. **Guided generation is constrained decoding at the token level.** Apple states (WWDC25 session 301, verbatim): "with constrained decoding, the model is prevented from making structural mistakes… For every token that's generated, there's a distribution of all the tokens in the model's vocabulary. And constrained decoding works by masking out the tokens that are not valid. So instead of just picking any token, the model is only allowed to pick valid tokens according to the schema." This closes your answer space at the sampling layer, not post-hoc. The Apple Tech Report (arXiv:2507.13575, §7) adds that an "OS daemon employs highly optimized, complimentary implementations of constrained decoding and speculative decoding to boost inference speed while ensuring that the model's output conforms." No Apple-published number quantifies guided-generation latency overhead; Apple frames it as net inference-accelerating.

2. **4,096 tokens is the documented, fixed ceiling — input+output combined.** Apple engineer confirmation (Developer Forums): "the on-device foundation model currently has a context window of 4096 tokens per language model session, and all the input and response in the generation process contribute tokens to the context window." iOS/macOS 26.4 added `SystemLanguageModel.contextSize` (returns 4096; `@backDeployed(before: 26.4)`) and `tokenCount(for:)`, so you can now query the limit rather than discovering it at failure. See TN3193.

3. **The static-briefing half is well-precedented and reliably outperforms runtime reflection.** AutoGuide (Fu et al., NeurIPS 2024, arXiv:2403.08978) generates context-conditional guidelines and its WebShop k-ablation (Table 4) found — notably — that **k=3 guidelines yielded the best performance**: "The k = 3 yields the best performance. The largest k value of 5 can lead an LLM agent to overthink, potentially resulting in a slight decrease in performance." Agent Workflow Memory (Wang et al., arXiv:2409.07429, ICML 2025) reports "AWM substantially improves the baseline results by 24.6% and 51.1% relative success rate on Mind2Web and WebArena." Contextual Experience Replay separately raised a GPT-4o WebArena baseline by ~51% (to 36.7%; Liu et al., 2025). This corroborates your nine-briefed-steps-vs-three-interventions observation.

4. **A model is probably the wrong mechanism for most of `wait`.** UI-test automation has solved synchronised waiting deterministically for years (Selenium explicit/fluent waits, Playwright auto-waiting on actionability). Your transition graph with p95-per-edge timing is exactly a learned wait policy; "has this screen historically taken longer than this?" is a lookup. Reserve the model for `stop`, which genuinely reads intent.

## Details

### Q1 — Operational envelope of Apple Foundation Models

**Q1.1 — Is 4,096 the documented ceiling? Input+output or input only? Varies by build/device? Queryable?**
Verified: 4,096 tokens, fixed, documented in TN3193 ("Managing the on-device foundation model's context window"). It is **input + output combined** — Apple's forum guidance: "all the input and response in the generation process contribute tokens." An Apple DTS engineer states: "This is always the fixed token limit, there's no possibility of it changing." It does **not** vary by device class for the on-device `SystemLanguageModel.default` (the ~3B model). It **is** now queryable: `SystemLanguageModel.contextSize` (iOS/macOS/visionOS 26.4, back-deployed) returns 4096, and `model.tokenCount(for:)` measures a prompt or transcript. Note the near-boundary error semantics: the error can fire at e.g. 4,092 tokens because the response needs headroom too. One caution flagged in third-party writing (Vadim Drobinin): the concrete type behind the `.unavailable` reason and guardrail behaviour has shifted across 26.x dot-releases, so pattern-match defensively and log the literal string. **You asked the wrong question earlier and this is the reframe**: don't ask "how big is the window" — ask "does my per-judgement input plus expected output fit under 4,096 with headroom," and enforce it with `tokenCount` before every call, because a fresh session per judgement (your current pattern) makes this a per-call budget, not a running one.

**Q1.2 — Session lifecycle: prune/condense transcript, or fresh session? Cost of a fresh session?**
There is **no supported transcript-pruning or entry-removal API**. TN3193 and Apple's guidance describe the intended recovery as: catch `exceededContextWindowSize`, then **start a new session**, optionally seeding it with a summary or the last-N `Transcript` entries you carry forward yourself (constructing a new `LanguageModelSession(transcript:)`). A widely-cited limitation (Developer Forums thread 817502): once you're in the `catch` block the in-session state is effectively lost — there is no in-place trim — so condensing must be done proactively before the wall, or by rebuilding. For your use case, **fresh session per judgement is the correct and intended pattern**, not a workaround. On cost: the instruction prefix is part of the prompt and is re-tokenised/re-prefilled per session; Apple has not published a per-session setup number, but WWDC26 session 339's provider protocol (`LanguageModelExecutor`) explicitly discusses "KV cache state reuse across calls," implying no automatic cross-session KV reuse for the system model. Prefer a short instruction prefix (see Q6.4).

**Q1.3 — Warming: is there `prewarm()`? Cheaper warm? Survives disposal?**
Yes: `LanguageModelSession.prewarm()` (and a `prewarm(promptPrefix:)` overload) is the supported warm — Apple's docs describe it as asking "the framework to load model resources ahead of a known upcoming request to reduce first-response latency." Apple guidance: redundant `prewarm()` calls are ignored; use it during idle time, not for proactive/untriggered suggestions. Your throwaway `respond` at startup is heavier than needed — `prewarm()` loads weights/prompt cache without a full generation. **Model residency is process/system-managed, not session-managed**, so a warm generally survives disposal of one session as long as the model stays resident (see Q1.5); `prewarm()` is per-session but the expensive part (weights in memory) is shared.

**Q1.4 — `@Generable` guided generation: latency cost or save? Enforced at sampling or validated after?**
**Enforced at sampling** — this is the decisive answer for your safety argument. Apple (WWDC25 301, verbatim): constrained decoding "works by masking out the tokens that are not valid," so "the model is only allowed to pick valid tokens according to the schema." Enums are explicitly covered (`@Generable enum` with cases; the macro compiles a schema at compile time). Tool calling is built on the same mechanism to "guarantee the structural correctness of tool calls by preventing hallucinated tool names or arguments" (Tech Report §7). **The layer at which your answer space is closed is the token-sampling layer** — a fourth word is masked out of the vocabulary distribution at each step, not rejected after the fact. Latency: no Apple number; Apple frames constrained + speculative decoding as a net speed-up. One field report (Developer Forums) flags a regression: "guided generation: empty token masks and severe slowdowns on macOS 27 betas 5, 6 and 7" (FB24310823) — worth watching if you move to 27.

**Q1.5 — Concurrency and residency: multiple sessions per process? Idle unload? Eviction by other apps?**
A single `LanguageModelSession` handles **exactly one request at a time** — check `isResponding` before sending; concurrent requests on one session throw `GenerationError.rateLimited` ("A session can handle only one request at a time"). You **can** hold multiple sessions in one process and even run them for parallelism, but they contend for the one shared on-device model, so true concurrency is limited. The model is a shared system resource (~3 GB RAM for the ~3B model) and is loaded/unloaded by the OS; Apple has not documented an idle-unload timeout, and cross-app eviction behaviour is not documented — treat residency as best-effort and re-`prewarm()` on demand. **Nobody has published a measured idle-unload interval or an eviction rate.**

**Q1.6 — Availability reasons and guardrails: full set documented? Benign refusals?**
`SystemLanguageModel.Availability.UnavailableReason` has three documented cases: `.deviceNotEligible` (permanent — hide the feature), `.appleIntelligenceNotEnabled` (user setting — prompt once), `.modelNotReady` (downloading/transient — retry). Treat these as a closed set but keep an `@unknown default`. Guardrails **do** refuse benign content: developers report `guardrailViolation` on non-sensitive prompts, sometimes driven by a Siri/OS language mismatch rather than content; WWDC 2026 session 241 reportedly reduced the guardrail false-positive rate between iOS 26.4 and the iOS 27 model. **The benign-refusal rate is not published** — you would need to measure it on your own UI-text corpus. Your current handling (a refusal → "no answer" → executor default) is the safe choice; instrument it so you can report the rate. The full `GenerationError` set is documented: `exceededContextWindowSize`, `guardrailViolation`, `unsupportedGuide`, `unsupportedLanguageOrLocale`, `assetsUnavailable`, `decodingFailure`, `rateLimited` (and, in the Python SDK mirror, concurrency errors). Triage them differently — `exceededContextWindowSize` is recoverable by rebuilding the session; `guardrailViolation` and `unsupportedLanguageOrLocale` are not, so a blanket retry loop wastes battery.

**Q1.7 — Published latency/throughput on M-series for short guided calls, with N and chip?**
No Apple guided-generation micro-benchmark with N exists. The nearest primary number, from Apple Machine Learning Research ("Introducing Apple's On-Device and Server Foundation Models," verbatim): "on iPhone 15 Pro we are able to reach time-to-first-token latency of about 0.6 millisecond per prompt token, and a generation rate of 30 tokens per second," adding "this performance is attained before employing token speculation techniques." (This is A17 Pro / iPhone 15 Pro, not an M-series Mac, and not a guided-generation-specific figure.) Third-party (HackerNoon) reports 30–50 tok/s on iPhone 15 Pro, degrading under concurrent Neural Engine load and with context size. Community Apple-silicon benchmarking exists (john-rocky/apple-silicon-llm-bench) but treats Apple FM as a single opaque model. Your measured **640 ms per consultation** and **987 ms → 1,890 ms** latency climb as the transcript grew are consistent with the documented "performance degrades with context size" behaviour — which your fresh-session-per-judgement fix directly addresses.

**Node integration (flagged).** The framework is Swift/ObjC only. As of macOS 26 you reach it from Node **only via a Swift helper process**. macOS 27 (WWDC26 sessions 334/339) ships a pre-installed `fm` CLI and a Python SDK (`pip`), and opens the framework to third-party providers via `LanguageModelExecutor`. There are community npm bridges (`apple-fm`, Developer-ID-signed/notarized, which shells to a helper) — **using one would add a runtime dependency and needs an owner decision**; a hand-rolled Swift helper keeps your "MCP SDK only" invariant. No shipped ML weights are involved in either case (the model is system-provided).

### Q2 — Is a closed three-word answer space a known pattern, and is three right?

**Q2.1 — What is it called / what to read.** Three overlapping literatures: (a) **constrained decoding / guided generation** (the enforcement mechanism — Apple's guided generation; general surveys of grammar/regex-constrained decoding); (b) **selective classification / classification with a reject option** (Chow 1970; El-Yaniv & Wiener 2010; Geifman & El-Yaniv 2017 SelectiveNet) — the framework for a classifier that may abstain; (c) **LLM-as-judge with a closed rubric** (Zheng et al. 2023, MT-Bench). Your component is best described as a **constrained-decoding LLM-as-judge over a closed label set** — read the selective-classification line for the abstain question and the LLM-as-judge line for the bias question.

**Q2.2 — What is measured about small models on k-way decisions (calibration/accuracy as k grows)?** The relevant finding (arXiv:2402.13213): chat-LLM maximum-softmax-probabilities are **miscalibrated on multiple-choice but still predict correctness**, and correctness-prediction (not calibration) improves with capability. AutoGuide's k-ablation is the most on-point external datapoint: **k=3 beat k=1 and k=5** for context-aware guidance, i.e. a small closed set was empirically the sweet spot in an agent loop. There is no clean published "3-way vs 5-way from the same small model" calibration curve for exactly your task — **nobody has measured your specific k=3-vs-k=5 reliability delta**; the general direction (fewer options → higher per-decision reliability, up to a point) is supported but not quantified for your setting.

**Q2.3 — Is three the right three? Granularity and an abstain token.** Both your problem rulings were **missing-vocabulary** cases (needed zoom-out; content scrolled past), not reasoning errors. The literature's answer is the **reject/abstain option**: adding an explicit `abstain` (⊥) token is the one addition that increases coverage **without widening what the component can do** — it maps to your existing safe default (no answer → executor proceeds as if unsupervised). This is exactly selective prediction (Chow's error-reject trade-off; El-Yaniv & Wiener's risk-coverage), and it is the specific place your item 97 (conformal abstention) should be applied first. Adding a *fourth action word* (e.g. "zoom") would widen the action space and cost the safety property; adding a *fourth abstain word* does not. **Prefer abstain over any new action.**

**Q2.4 — Do LLM-as-judge pathologies apply at k=3?** Position, verbosity, and self-preference biases are well documented (Zheng et al. 2023; Wang et al. 2023 "LLMs are not Fair Evaluators"). They are studied mostly for pairwise A/B comparison; your task is single-item classification into a fixed vocabulary, so **position/verbosity bias largely don't apply** (there is no candidate ordering, no length comparison). The residual risk is **option-order sensitivity** in how you present the three words and **prompt-phrasing sensitivity**. Both mitigations are cheap at your 640 ms budget: randomise the option order across calls and/or take self-consistency over a few samples. Recent large-scale judge audits suggest verbosity sensitivity has fallen in newer models, but do not assume it for a ~3B on-device model — measure it.

### Q3 — Briefing versus intervention: has anyone ablated this?

**Q3.1 — What the static half is called.** "Context-aware guidelines" (AutoGuide), "workflow memory" (Agent Workflow Memory), "contextual experience replay," "environment notes / affordance hints," "skill library" (Voyager). For search, **"context-aware guidelines" and "agent workflow memory"** are the most productive terms; your `supervise`/`expect` strings are exactly AutoGuide-style conditional guidelines written at plan time.

**Q3.2 — Has anyone ablated static context vs a runtime critic and reported the split?** Not as a clean head-to-head with your exact framing, but the closest numbers all point the same way as your data: Voyager without its skill library lost **15.3× in milestone speed** (the skill library "was the performance"); AWM reports **24.6% (Mind2Web) and 51.1% (WebArena) relative success-rate gains**; Contextual Experience Replay lifted a GPT-4o WebArena baseline ~**51%** (to 36.7%); Generative Agents degenerated within 48 simulated hours without reflection. These consistently show **static/accumulated context often outweighs the model backbone or the runtime critic**. **Nobody has published the exact "briefing-only vs critic-only vs both" 2×2 for a UI agent** — that gap is precisely your item 96, and the "briefing, no model" arm you have not run is the one that would settle attribution.

**Q3.3 — Learning/accumulating briefings across runs.** Strong precedent: AutoGuide (generate guidelines from offline experience), ExpeL (distil transferable insights/rules), AWM (extract reusable workflows), Voyager (skill library), CLIN (continually-updated causal abstraction), ACE (Generator/Reflector/Curator "context playbook," reported +10.6% on agent benchmarks). Your per-screen transition graph is the natural store: attach the note-that-would-have-prevented-a-failure to a `(screen_hash)` node and offer it to the next run's planner. This is a well-trodden design.

**Q3.4 — Do briefings decay or mislead (stale note worse than none)?** Yes, and this is a documented, named failure mode — the exact "confidently-wrong" pattern you keep rediscovering. "Honest Lying: Understanding Memory Confabulation in Reflexive Agents" (arXiv:2605.29463) shows **reflective memory can be actively harmful**: a no-memory ablation solved environments that the memory-augmented agent could not, and a confabulated rule with two votes becomes entrenched and misapplied everywhere (ExpeL-style rule libraries amplify this). Du (2026) names the central risk as "self-reinforcing error." **Mitigation the literature suggests**: version briefings against `screen_hash`, expire/revalidate them when the screen signature changes, and prefer programmatic/parsed failure signals over open-ended self-diagnosis (the same paper raised correct-object mention from 0% to 86% by replacing open-ended reflection with parsed trajectory signals).

### Q4 — When should a critic be consulted at all?

**Q4.1 — Invocation policy and net cost.** Named policies: Reflexion (reflect after a failed attempt), Self-Refine (iterative critique-revise), CRITIC (tool-grounded verification before accepting a revision), verifier-guided decoding, AutoMix (self-verification decides escalation). **Most report accuracy, not net cost.** The honest state: Self-Refine reported ~20% absolute average improvement across seven tasks; Reflexion 80%→91% pass@1 on HumanEval — but the practitioner consensus (and cost-focused write-ups) is that gains concentrate in passes 1–2 and each reflection pass costs ~2–3× tokens, so cap iterations. Your **on-failure-only** policy is the cheap end of this spectrum and is defensible; the literature does not give a clean "consult-always vs on-failure" net-cost curve for UI agents — **that specific net-cost comparison is unmeasured.**

**Q4.2 — Pre-action plausibility check vs post-failure critic at equal cost.** AutoMix and "firewall routing" (block a query from a weak model when predicted failure is high) are pre-action checks; CRITIC grounds critique in tool feedback. There is evidence that **grounded/pre-emptive checks beat ungrounded self-critique** (the "coherence trap": intrinsic self-critique without external signal often fails). But **no paper cleanly shows pre-action beats post-failure at equal cost for a UI executor** — your before-vs-after choice is not settled by data. Given your executor already verifies each step locally (a grounded signal), post-failure consultation is the well-matched design; a pre-action plausibility check would only pay off where a failure is expensive to *attempt* (destructive taps), which argues for a targeted pre-check on irreversible steps rather than a blanket switch.

**Q4.3 — Early abandonment savings quantified separately?** Your `stop`-truncates-the-batch behaviour is early stopping / early abandonment. It is widely used (cap iterations; escalate-or-stop in cascades) but **rarely isolated as a savings figure** distinct from per-step correction. OSWorld-Human's finding that agents take 1.4–2.7× (up to 4.3×) more steps than the human-minimum path implies large headroom for abandoning doomed trajectories, but **the specific "savings from early abandonment alone" number is not published** — you would be measuring something genuinely under-reported, which is worth doing cleanly.

### Q5 — How to honestly report a saving like this

**Q5.1 — Standard cost model separating calls / input tokens / output tokens / wall clock.** FrugalGPT (Chen, Zaharia, Zou, arXiv:2305.05176) reports cost as $ per query against a fixed budget and demonstrates matching "the performance of the best individual LLM (e.g. GPT-4) with up to 98% cost reduction" via cascades; RouteLLM (Ong et al., arXiv:2406.18665, ICLR 2025) reports its matrix-factorization router achieving "85% cost reduction on MT Bench at 95% of GPT-4 quality, routing only 14% of queries to GPT-4." The emerging convention worth adopting is **normalized token cost** (weight input and output tokens by separate per-token coefficients, e.g. 0.01/input, 0.03/output) plus **escalation rate** and **wall-clock latency** as separate axes. For agents specifically, OSWorld-Human's **Weighted Efficiency Score (WES)** penalises inefficient successful and failed trajectories separately, and reports steps-vs-human-minimum. **Adopt: report (1) model calls, (2) input tokens, (3) output tokens, (4) wall clock, and (5) a step/efficiency ratio — do not collapse them**, precisely because, as you note, one saved call also removes a screenshot so calls and tokens are not proportional.

**Q5.2 — Is "recovery-call fraction" an established diagnostic?** Not under that name. OSWorld-Human's decomposition is the closest published relative: it finds "LLM calls for 'Planning' and 'Reflection' are the main culprits, consuming **75–94% of total task time**" while pure tool action is a small remainder — i.e. "deliberation/recovery overhead as a fraction of total" is exactly the quantity you're capturing, but the field measures it as a time/step fraction, not a "recovery-call fraction." **Your 58%→28% is effectively a coinage**; frame it as "share of model calls spent on failure recovery," cite the OSWorld-Human deliberation-fraction result (arXiv:2506.16042) as the analogous published metric, and define it explicitly so readers can reproduce it.

**Q5.3 — Honest reporting of a confounded-but-real improvement.** The win (25 vs 45 calls, both arms completing every field) is not in doubt; only attribution is. The correct move, per ablation-reporting norms and ML reproducibility checklists: **report the aggregate improvement as real, state plainly that treatment (briefing) and mechanism (critic) are confounded, present the three intervention firings honestly (one right, one defensible, one wrong), and pre-register the missing "briefing, no model" arm as the attribution test.** Explicitly note your own noise band (2.2–6.0 points by run selection; 15–22% task flakiness) and that the A/B does not clear it. This is the publishable, non-overclaiming framing.

### Q6 — Would a different local model help, and what would it cost?

**Q6.1 — Small vs large on short closed-vocabulary judgements.** The evidence favours your reasoning. For small state spaces / small label sets, small models learn the decision quickly and the large-model advantage concentrates on **uncertain** inputs (multiple works: "the larger models' advantages over smaller ones appear when the [smaller model is] not uncertain"). "Thoughtful Things" (SLMs for smart devices, arXiv:2405.03821) found small state spaces are learned fast and most small-model errors were invalid-output/format issues — which constrained decoding already eliminates for you. So **capacity is very unlikely to be your binding constraint at k=3**; there is no published result showing a 70B beating a 3B on a well-posed 3-way UI judgement, and your one wrong ruling was a vocabulary gap, not a reasoning gap. **This settles the direction, though nobody has run exactly your k=3 3B-vs-70B comparison.**

**Q6.2 — Other system-provided inference paths on macOS.** Beyond `SystemLanguageModel`: the **`fm` CLI** (pre-installed, macOS 27) and the **Foundation Models Python SDK** (macOS 27) are new system surfaces to the same model; Core ML, the Natural Language framework, and Vision are system-provided but are not general text-judgement LLMs; Writing Tools / Apple Intelligence are not a programmable judgement API. **The only system-provided general LLM is `SystemLanguageModel`** — which is exactly why it satisfies your two hard non-goals (no shipped weights, no new dependency). PCC (`PrivateCloudComputeLanguageModel`, behind the `com.apple.developer.private-cloud-compute` entitlement, 32K context) is system-provided but off-device and needs a network + entitlement decision.

**Q6.3 — User-supplied server (Ollama/llama.cpp/MLX) — flagged for owner decision.** **This would break both non-goals**: it adds a runtime dependency and (for llama.cpp/MLX/Ollama) requires shipping or downloading model weights. **It needs an explicit owner decision, not a quiet adoption.** What it would buy: a larger context window (removing the 4,096 constraint), a bigger model (marginal at k=3 per Q6.1), and provider flexibility — but at the cost of your "MCP SDK only / no weights" invariant and added operational surface. Recommendation: **do not adopt** unless a measured k=3 accuracy gap or a context-window need emerges that the system model cannot meet. (Note: macOS 27's `LanguageModelExecutor` provider protocol would let you plug such a model in behind the *same* Swift API — but it is still a dependency + weights decision.)

**Q6.4 — Is the instruction prompt the cheaper lever?** Likely yes. Your ~350-word instruction is re-tokenised per fresh session, so it is a recurring cost on every judgement. There is no Apple-published instruction-length-vs-quality curve for the on-device model, but Apple's own guidance is to keep instructions and tool definitions lean against the 4,096 budget, and guided generation is explicitly designed so that **format instructions can be removed from the prompt** (the schema carries them). **Try first**: move all format/vocabulary specification into the `@Generable` enum schema and cut the instruction to the evidence-ordering rule only; measure decision quality and per-call latency with `tokenCount`. This is the cheapest experiment and directly attacks your per-session prefill cost.

### Q7 — Is a model the right mechanism for `wait` at all?

**Deterministic/history-based wait is a solved pattern in UI automation.** Selenium's explicit and fluent waits and Playwright's auto-waiting on actionability synchronise on observable conditions rather than a judgement; the whole discipline exists to remove timing guesses. Your transition graph with **p95-per-edge timing already is a learned wait policy** — "has this edge historically taken longer than p95 to arrive?" is a lookup, and `retry` (moment was wrong) is similarly amenable to a history/backoff rule. **Nobody has published the exact fraction of a UI critic's `wait`/`retry` rulings a history lookup would have recovered** — that is an unmeasured but highly answerable question on your own logs, and if the answer is "most of `wait`," the right shape is a **two-stage cascade**: the graph answers first, the model sees only what the graph cannot (chiefly `stop`, which reads plan-level intent). This mirrors FrugalGPT's cheap-first cascade and is directly aligned with your instinct.

**On proxies and knowing when to refuse to rule.** The body of work you want is **selective prediction / conformal abstention** (Chow 1970; El-Yaniv & Wiener 2010; Geifman & El-Yaniv; recent conformal-abstention and calibrated-selective-classification work, e.g. arXiv:2208.12084). It tells a small judge **when to abstain rather than rule** via a risk-coverage threshold calibrated on a small held-out set — exactly the discipline that would have caught both your mis-rulings (both should have been abstentions). This is your item 97, and Q7 is the specific place to apply it first: the model rules only on the covered region where it is calibrated-confident, and abstains (→ safe executor default) elsewhere.

## Recommendations

1. **Ship the context-window fix as the settled state and instrument the budget (do now).** Keep fresh-session-per-judgement; add a `tokenCount`-based pre-check against `contextSize` (26.4+) so you never re-enter the `exceededContextWindowSize` path; replace the throwaway `respond` warm with `prewarm()`. Benchmark: first-real-judgement latency should stay ≤ ~600 ms and no `exceededContextWindowSize` in a 200-failure soak.
2. **Add an explicit `abstain` token to the enum before running the 2×2 (do next).** It is the one vocabulary addition that raises coverage without widening the action space, maps to your existing safe default, and directly fixes your two missing-vocabulary mis-rulings. This is the concrete first application of item 97.
3. **Run the missing "briefing, no model" arm as the attribution test within item 96.** Report calls, input tokens, output tokens, wall clock, and a step/efficiency ratio separately (OSWorld-Human/WES convention); define your recovery-call fraction explicitly; state the confound and your noise band plainly. Threshold that would change the design: if briefing-only recovers ≥ ~80% of the calls that briefing+model does, downgrade the model to a `stop`-only / abstain-capable cascade stage.
4. **Prototype the graph-first `wait`/`retry` cascade and measure recovery fraction on existing logs (cheap, high-information).** Compute what fraction of past `wait`/`retry` rulings a p95-edge lookup would have gotten right. Threshold: if ≥ ~70%, restructure to graph-first-model-second and consult the model mainly for `stop`.
5. **Trim the instruction prompt into the schema (cheap experiment).** Move format/vocabulary into the `@Generable` enum, cut instruction to the evidence-ordering rule, measure quality and per-call latency. Keep only if decision quality is unchanged.
6. **Version briefings against `screen_hash` and expire on signature change.** Directly mitigates the documented stale-memory/confabulation failure mode; prefer parsed failure signals over the logged prose reason (which you already correctly hide).
7. **Do not adopt Ollama/llama.cpp/MLX or a community Node bridge without an owner decision.** Both break a hard non-goal (dependency and/or shipped weights). A hand-rolled Swift helper preserves "MCP SDK only." Revisit only if a measured k=3 accuracy gap or a hard context-window need emerges.

**On the ordering of items 96 and 97:** **Promote 97 (selective prediction / conformal abstention) ahead of 96.** Both of your problematic rulings were abstention cases, not experiment-design questions; the abstain token is cheap, preserves the safety property, and is the highest-reliability-per-effort change available. Run 96 immediately after — its critical arm is "briefing, no model," which is the only thing that resolves attribution — but the reliability win sits in 97, and filing it behind 96 repeats the "research instead of act" habit you're trying to break.

## Caveats
