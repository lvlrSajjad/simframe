simframe.

Always-warm iOS Simulator frames for coding agents.

An agent driving the iOS Simulator spends most of its time waiting on screenshots. simframe keeps the newest frame permanently warm in the background, so looking at the screen stops being something you wait for.

GitHub npm MIT macOS · Node ≥ 18.17

The problem

Every “let me check the screen” is a fresh simctl io screenshot: a process spawn, a framebuffer grab, a file write, an image encode. That is roughly 130 ms of pure blocking latency, paid again on every single look — and paid twice whenever the agent captures mid-animation, sees a half-drawn frame, and has to look again.

screenshot  →  spawn simctl → grab → encode → image~130–400 ms
sim_look  →  read the frame that is already there → image~20 ms
sim_state  →  read 300 bytes of JSON → text, no image~2 ms

Install

# Claude Code
claude mcp add simframe -- npx -y simframe mcp

# or use it directly
npm install -g simframe
simframe doctor

Nothing to configure. Capture starts on the first call, targets the booted simulator, and stops itself 15 minutes after the last request.

Baselines: the thing to understand

Every change question is really “changed since when?” — and the answer is almost never “since the previous frame”. A UI transition is over in about 700 ms, so comparing consecutive frames tells a caller that polls every few seconds “nothing changed”, even though the screen is completely different from when it last looked.

So simframe compares against the last frame you observed. Over MCP that is automatic — each call remembers what it showed you. From the CLI you capture a baseline before acting: 

H=$(simframe mark)          # hash of what is on screen now
# ...tap, launch, navigate...
simframe wait --since=$H    # change, then settle
simframe state --since=$H   # what moved, as text

It remembers the last minute

Looking only at the newest frame is like having no short-term memory: if the screen is already different by the time you look, the change is simply gone. simframe keeps every frame for the last 6 seconds, thinned to about 2 fps out to 60 seconds — and reads that memory back as text first.

The part that pays for itself

A screen hash and a 4×8 movement grid cost a couple of hundred bytes, so an agent can poll as often as it likes and spend image tokens only when there is genuinely something new to look at.

How it works

┌───────────────────── background, one loop per simulator ─────────────────────┐
│   xcrun simctl io screenshot  ──►  sips -Z  ──►  decode PNG  ──►  compare    │
│         ~130 ms                     ~30 ms         ~6 ms                     │
│                                     │                                        │
│                 rename into ~/.simframe/<udid>/                              │
│                 latest.png · ring/<seq>.png · state.json                     │
└──────────────────────────────────────────────────────────────────────────────┘
                                      │  a rename is atomic
┌─────────────────────────────────────▼────────────────────────────────────────┐
│   MCP server / CLI: stat + read.  No simctl anywhere in the request path.    │
└──────────────────────────────────────────────────────────────────────────────┘
  • Files are the IPC. The loop renames completed frames into place and readers just read them. A rename is atomic, so a reader can never see a half-written frame — and there is no socket, port or protocol to get wrong.
  • Zero image dependencies. Resizing uses sips, which ships with macOS. PNG encode/decode and all frame comparison are a few hundred lines of plain JavaScript over node:zlib. The only runtime dependency is the MCP SDK.
  • It backs off when nothing is happening. 4 fps while the screen moves, 1.5 fps once it has been still for 2.5 s, snapping back instantly on change — 1.1 % CPU idle, 3.1 % active.
  • Comparison happens on a small grayscale grid, which is why “did anything change?” costs microseconds. The hash is a 128-bit mean-threshold hash: the same screen always hashes the same, even though the bytes simctl emits are not stable frame to frame.
  • One writer per device. Ownership lives in meta.json; a second loop refuses to start and a superseded loop retires itself, so two loops can never overwrite or prune each other’s frames.
  • Capture ignores the window. simctl reads the framebuffer, so frames keep flowing while the Simulator is hidden, buried behind other windows, or on another Space.

Honest limitations

  • Simulators only — simctl cannot capture a physical device.
  • simframe reads the screen; it does not tap, swipe or type. It sits alongside whatever already drives input and replaces only the screenshot.
  • It speeds up confirming a fix, not locating one. A bug living in a memo comparator or a stale closure is not visible in any frame.
  • Capture tops out near 6 fps, because simctl io screenshot costs ~130 ms. Fast animations are sampled, not recorded.
